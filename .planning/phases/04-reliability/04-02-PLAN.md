<objective>
BGP context propagation + BGP error surfacing.

Purpose: (A) The BGP subsystem builds its context from context.Background(), severing it from daemon lifecycle — replacing that with a child of the daemon context means shutdown cancellation reaches every BGP API call. Verified against GoBGP v3.37.0 source: AddPath/DeletePath do NOT consume ctx (pure plumbing, zero behavior delta today), ListPath DOES honor ctx mid-iteration (early stop during teardown is acceptable — RIB is already being torn down by StopBgp which runs BEFORE s.cancel() in Shutdown). (B) Advance/Withdraw failures are either silently discarded (`_ = bgp.Advance(...)`) or logged at Error with zero structured context — consolidating to exactly one structured Warn per failed path operation, carrying the op, the IP, the router ID, and configured peer IPs.

D-06 design decision (resolved this planning round, within ROADMAP SC-4 bounds): log INSIDE the Advance/Withdraw closures in internal/bgp/main.go — the single choke point reachable from every current and future caller, with s.id/s.peers/_bgp.L() in scope. The eviction call site (cache.go) keeps its own log line because it contributes business context (the evicted FQDN) the transport layer cannot know; its severity is downgraded Error→Warn for consistency. The "bgp: not initialized" early-return error (global unset) stays unlogged by design — that state implies DNS cannot be answering yet.

No external behavior change: same routes announced/withdrawn, same shutdown ordering, same failover semantics.

Output: Cancellable BGP context threaded from daemon, one structured Warn per BGP op failure, full suite green.
</objective>
