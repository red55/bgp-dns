<objective>
Support optional BGP peer authentication (SEC-04): an `AuthPassword` field on each configured peer flows from YAML through the Phase 3 DI config struct into the GoBGP `bgpapi.Peer` spec at `AddPeer` time, where GoBGP applies it as the RFC 2385/5925 TCP-MD5 session key (`setTCPMD5SigSockopt`) when non-empty. Absent or empty means no authentication — byte-for-byte today's behavior.

Purpose: Operators whose edge router enforces TCP-MD5 session authentication can connect bgp-dnsd; operators who don't are unaffected (opt-in by config presence).

**Decision D-05-P6 (adopting research Open Question 3):** evidence for the config→spec wiring comes from EXTRACTING a small pure helper `buildPeerSpec` in internal/bgp that assembles the per-peer `*bgpapi.Peer`, unit-tested for the AuthPassword mapping (set→propagated, unset→empty). Extraction is the preferred path because the loop wiring is a straightforward literal-move; the documented fallback (inline one-line addition + human-verify checklist item instead of the unit test) triggers ONLY if the extraction fights the existing loop wiring (more restructuring than a verbatim move) — in that case the executor MUST record which path was taken and why in the SUMMARY. TCP-MD5 chosen over RFC 9972 ChaCha20-Poly1305 solely because pinned GoBGP v3.37.0 exposes only the MD5-style knob (accepted trade-off, research-verified).

Expansion task completing the fourth leg of Phase 5 alongside the tracer (05-01) and data-plane filter (05-02).
</objective>
